# Drivetrain request boundary

`controls` is independent Java 17 code intended only for a robot-facing adapter when the application chooses to install it. It has no WPILib, World-State, GUI/server, learned-service, NT, or hardware dependency. It does not implement a drivetrain, command scheduler, follower, pickup controller, or persistent-track selector.

Use `DriveRequests.prepareDriveToPose`, `prepareDriveToSelectedObject`, or `prepareDriveToCluster` to validate a request and invoke your real `TrajectoryPlanner<T>`. Then call `constructCommand(prepared, bindings, teamFactory)` to construct an unscheduled application-owned command. Neither helper invokes a drive or follower port. A factory that moves or schedules the robot during construction violates this interface.

Provide a canonical fixed-origin field pose in NWU meters and yaw radians, measured **robot-relative** speeds, a robot monotonic nanosecond clock, explicit epoch/reset/world identities, field bounds, motion limits, age/work limits and start-drift tolerances. Bind the state provider, planner, follower, drive port, cancellation and possession sensors explicitly. Missing bindings produce `MISSING_BINDING`; no stationary state or no-op hardware fallback is supplied. The construction result either contains a command or one bounded structured rejection.

The planner receives the exact goal, initial measured state and limits. It must return an actual trajectory plus `PlanEvidence` matching this request, goal, frame, initial measured state, applied motion limits, field bounds and time, and attest reachability, footprint clearance, field bounds and motion limits. A cached plan for different initial speeds, looser limits or a different map bound rejects even if it has the same request label. The trajectory is opaque to this library: those assertions come from the application's real planner/validator, and this library cannot independently establish collision avoidance or dynamics. The application must keep that trajectory immutable and use a planner with a bounded runtime. Plan sample, age, duration and length limits are checked here, but they cannot interrupt a blocking external callback.

World-State owns object and cluster selection. Map its already selected safe **approach pose** into `PersistentGoal`, and supply the originating source-set revision, selection revision, robot epoch/reset/world identity, ordered selection/world/oldest-member times, reachability/footprint clearance result and globally unique persistent member IDs. An object must contain exactly one ID. A cluster must contain two or more distinct IDs and fit the configured member bound. Counting bounding boxes, reselecting the nearest raw packet target, or fabricating a cluster from repeated camera observations does not meet this contract. IDs must identify the track in its owning world context; bare camera-local track numbers do not suffice. The World-State selector remains responsible for usefulness, deduplication, obstacle geometry, hysteresis and authoritative selection changes.

Pickup requests reject existing possession before planning and again before command construction. Drive-to-pose is a general motion request and does not stop merely because possession is present. Cancellation is checked for every request. Planning and construction resample the clock/state and reject stale/future data, reset/world/epoch changes, unsafe evidence and start-pose/speed drift. The final validation resamples time after state/sensor callbacks return, so a slow callback cannot extend a state, plan or selection lifetime. This detects late returns; it cannot interrupt or impose a runtime budget on an external callback. `validateBeforeStart` can be used immediately before starting an unscheduled command. It includes start-drift checks and is therefore unsuitable as a running-plan check once the robot has moved away from that start.

The existing robot/World-State command owner must manage the full execution lifecycle: schedule and cancel its command, validate ongoing authoritative goal selection and resets, read live pose/speeds and sensors, enforce limits, call its follower and drive port, stop on failure/cancellation/completion and use the single existing pickup controller where applicable. This module does not supply that state machine. No callback here bypasses robot-owned estimator or motion policy.

`NoMotionExample.constructPoseCommand` is a compile-tested generic integration shape. Its `main`/`run` uses explicitly synthetic CPU-only data and a synthetic trajectory handle, constructs an unscheduled object and asserts zero drive/follower invocations. It is not a ready-to-drive command or physical qualification. Installing an artifact does not change the actual robot-integration hold.

The dependency-free `DriveRequestsTests` main exercises construction, explicit callback binding, genuine preparation handoff, cancel/possession, reset/world/time/freshness boundaries, persistent-ID deduplication, clearance/reachability, plan bounds and failures. Hardware and real drivetrain/follower behavior require separate application integration and physical evidence.
